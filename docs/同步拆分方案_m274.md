# 全量 NBT 同步拆分方案（外部审计第一批第 3 条 · m274 方案稿，待作者拍板后实施）

## 一、现状链路与成本账（2026-08-06 实测于 7578a4a）

**链路**：`syncToClient()` = `world.updateListeners(NOTIFY_ALL)` → vanilla
`BlockEntityUpdateS2CPacket.create(this)` → `toUpdatePacket()`/`toInitialChunkDataNbt()` →
**完整 `writeNbt`**。

**包内容 = 存档级全量**：machineNodes（节点栈列表，每台机器 ItemStack 含全部配置 NBT：
坐标/升级/过滤/目标/阶位……上限 512 台）、connections、groups、items 背包、internalBuffer 全表、
nodeBufs 每节点缓存表、boundPanelPos/Dim、running、xpPool、forceChunks、nodeStat、nodeWhy、
storEnds、storEdges、storNodePos、busTop、prodPM、chunkOwned。

**接收方 = 所有追踪该区块的客户端**（vanilla 区块追踪广播）——路过的玩家没开画布照样收全量。

**触发点 30 处**：29 处事件同步（每次 C2S 写操作成功后立即广播：insertMachine/fuseNode/
togglePause/toggleSwitch/toggleFilterEntry/setSensorConfig/setNodeTarget/setNodePos/removeNodeAt/
ejectOne/组四操作/toggleConnection×2/toggleStorageEdge×2/setStorageNodePos/dockStorageNode/
scanStorageEndpoints/syncNow/tickInner 三处）+ 1 处周期同步（200t pos 哈希错峰，
有观众才发，m218 已治）。

**放大器（审计点名）**：单个写包 → 全量 NBT × 追踪玩家数。m269 的 writeBudget（40 包/tick/玩家）
只治了**入口**洪泛频率，每包的**出口**成本仍是 O(整个存档 × 追踪者)。拖动一个节点 = 每帧一次
全量广播。

**已备好的对表尺**：`CoreProfiler.syncPackets/syncBytes`（m177 特意埋的，注释原文
"增量同步改造前后在此对表"）。

## 二、客户端真实消费面（grep 实测，快照内容边界）

画布屏 `be()` 直读客户端 BE（数据由 vanilla 包 readNbt 填入），消费的 getter 全集：
`nodes`(×21)、`nodeStatus`/`nodeReason`（独立列表 nodeStat/nodeWhy）、`connections`、
`groupsView`、`storageEdgesView`/`storageEndpointsView`/`storageEndpointDimsView`/
`storageNodeX/Y/Placed`、`busTopIdsView`/`busTopCountsView`、`prodPerMinView`、
徽章 `nodeSpeed/nodeCount/nodePar`（读**节点栈 NBT** 的 spd/cnt/par，随 nodes 走）。

**三处兼容点已核实**：
1. 画布 handler **无槽位**——items 背包客户端从不需要（其他屏各有自己的 handler 管槽位同步）；
   小统计走 handler 的 10 位 PropertyDelegate，与 BE NBT 同步无关。
2. BER 全息动画（StructureCoreHoloRenderer）只读 `getWorld().getTime()`，零数据字段依赖。
3. m89 CanvasEnds/Homes 已是**"定向发 payload → 写客户端 BE 字段"的在树先例**
   （遍历 playerList 找 currentScreenHandler 匹配的观众 → ServerPlayNetworking.send），
   照抄管线零新模式。

**客户端确定不需要（可从同步中剔除）**：items、forceChunks、chunkOwned、boundPanelPos/Dim。
**实施第一步定向核对**（可能可剔）：internalBuffer 全表、nodeBufs 全表（徽章不读它，但节点
菜单/悬停是否显示缓存内容需核）、xpPool、running（nodeStatus 的"核心停机=灰"是否服务端
已折进 nodeStat 值，还是客户端读 running 判定——决定 running 是否进快照）。

## 三、方案 A：观众定向渲染快照 + 标脏聚合（推荐首刀）

1. **快照编码收口**：新私有函数 `writeRenderNbt(nbt, lookup)` = 第二节消费面字段子集；
   存档 `writeNbt` 改为"调它 + 追加存档专属字段"——**一份代码两处用，字段永不漂移**。
2. **新 S2C payload** `CanvasSnapshotPayload(BlockPos, NbtCompound)`：注册/发送照抄 m89 管线。
   收端客户端 handler：`world.getBlockEntity(pos)` instanceof SCBE → `applyRenderSnapshot(nbt)`
   （只写渲染字段，= readNbt 对应子集）。**画布屏 be() 读法零改动**。
3. **syncToClient() 内部换实现**：改为 `canvasDirty = true`——**29 个调用点零改动**。
   tickInner 尾部：`if (canvasDirty) { 对观众定向发快照; canvasDirty = false; }`
   无观众也清标（数据在服务端，靠开屏首包兜底）。
   → 同 tick N 次写**合并成至多 1 包/tick/观众**；非观众玩家零成本。
   拖动节点从"每帧全量广播全区块"降为"每 tick 一份快照只发看画布的人"。
4. **开屏首包**：打开画布（createMenu/OpenScreen 侧）对该玩家定向发一次快照——
   打开即见数据，不等周期。这是撤掉 updateListeners 后的**必做兜底**。
5. **toInitialChunkDataNbt 瘦身**：改调 writeRenderNbt——区块追踪初始同步从存档级降到渲染级
   （顺手治"路过玩家收全量"）。toUpdatePacket 保持 vanilla 默认或一并走瘦身 NBT。
6. **200t 周期同步保留**，改发快照 payload（自愈兜底，防标脏遗漏类 bug 永久性失同步）。
7. **对表**：prof.syncPackets/syncBytes 移到快照编码处，改造前后 `/sdzjz profile core` 对表。

**为什么不直接上增量**：29 个触发点语义各异，先用"标脏聚合 + 观众定向 + 内容瘦身"三板斧
把 O(全量×追踪者×包数) 打成 O(快照×观众×1/tick)，量级对表后再决定增量值不值得做。

## 四、方案 B：分段 rev 增量（第二刀，按 A 的对表数据决定）

快照拆两段：**轻段**（nodeStat/nodeWhy/busTop/prodPM——高频小量）每次照发；
**重段**（nodes/connections/groups/storEnds 系——低频大量）挂 revision，服务端记 per-viewer
lastSentRev，rev 没变不发。已有 m218 storeRev 先例可照抄。
**已知风险点**：节点坐标 nx/ny 存在节点栈 NBT 里——拖动=改栈=重段高频化，增量收益被吃掉。
根治要把坐标抽出节点栈（动数据模型，架构红线），**除非 A 的对表证明必要，否则不做**。

## 五、风险清单

- m89 ends 通道与快照的 storEnds 三件套**双轨并行**：实施时核对客户端两份数据落点是否同字段，
  防打架；可借机收拢单轨（快照全包含则 m89 40t 同拍可退役），但首刀先并行跑稳。
- m196 拖动覆盖机制已保证"渲染永不读会被同步打回的坐标"——同步节流不会引入拖动回跳，
  但实测手感仍是验收项。
- 存档路径 writeNbt 语义零变化（只是内部拆函数）；老档零迁移。
- Fabric 模组双端同版本装配，payload 改造无跨版本协议包袱。
- 512 节点栈编码仍是快照大头——A 阶段接受，B 阶段治。

## 六、验收标准与里程碑切分（作者拍板后按此排）

验收：①写操作场景 syncBytes 降一个量级以上；②路过玩家（追踪不开屏）同步量降至渲染级
且事件写包对其零广播；③拖动/连线/换目标/开屏即见数据，手感零差异；④双人对表：
A 开画布操作，B 站旁边不开屏，B 的流量无尖峰。

- **m275**：writeRenderNbt 收口 + CanvasSnapshotPayload + 标脏聚合 + 开屏首包（核心刀）
- **m276**：toInitialChunkDataNbt 瘦身 + 200t 周期改快照 + m89 双轨核对收拢
- **m277**：profile 前后对表落 DEVLOG + 按数据决定 B 是否立项
