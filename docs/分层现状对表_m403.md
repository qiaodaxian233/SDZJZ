# 分层现状对表（m403）：顾问三层图 vs 本仓实际

> 一句话结论：**目录形状对上了，分层还没到位**——三层里最该胖的 Core 只占 9%，
> 而 `src/main` 一个源集同时兼着「MC 版本层 + 加载器层 + 大部分本该属于 Core 的业务逻辑」。
> 好消息是：**低垂的果实已经摘完了**，剩下的每一步都必须先抽口再搬，搬不动的地方正是接口该在的地方。

## 一、实测（2026-08-20，全库自动统计）

| 源根 | 文件 | 代码行 | 占比 | 顾问图里的位置 |
|---|---:|---:|---:|---|
| `common/src/main/java` | 23 | 2 427 | **9.2%** | Core（零 MC） |
| `src/main/java` | 127 | 23 400 | **88.9%** | 混层：MC 版本层 + 加载器层 + 大量 Core 业务 |
| `versions/26.2` | 5 | 499 | 1.9% | MC 版本层（只有 bootstrap） |

分类（m361 口径 A=零 MC / B=触 MC 业务 / D=客户端 / E=Mixin）：

| 源根 | A | B | D | E |
|---|---:|---:|---:|---:|
| `common/` | **23** | 0 | 0 | 0 |
| `src/main/` | **0** | 98 | 23 | 6 |

**A 类在 `src/main` 已经是 0**——意思是"零 MC 依赖、抬手就能搬"的文件一个不剩，全在 Core 里了。
后面每往 Core 搬一个文件，都得先给它触到的 MC/加载器 API 抽一个口。

## 二、更重要的一个数：85% 的行其实是业务逻辑

对 34 个 ≥120 行的文件逐行统计"这一行是否出现 MC 类型"：

```
代码 15 805 行，其中触 MC 仅 2 445 行 = 15%
StructureCoreBlockEntity  3522 行 → 触 MC 551 行（16%）
StructureCoreScreen       3074 行 → 触 MC 361 行（12%）
SuperBenchRecipes          960 行 → 触 MC   6 行（ 1%）
```

**85% 的行是纯游戏设计**（预算、游标、路由、账本、规划器、配方表），本来就该在 Core。
但它们不是"整文件可搬"，而是**逐方法、逐行与 `world.setBlockState`/`ItemStack` 交织在一起**——
所以这不是目录整理活，是接口抽取活。这解释了为什么 Core 只有 9% 却不代表方向错。

## 三、和顾问三层图的对应与偏差

顾问图：`Core → MC Version Adapter → Loader Adapter`。本仓现状：

| 顾问的层 | 本仓现在是什么 | 差在哪 |
|---|---|---|
| Core | `common/` 23 文件，**零 MC 依赖** | 只有 9%；且比顾问的 Core 更严格（顾问的 Core 允许见 MC 类型） |
| MC Version Adapter | `versions/26.2`（仅 bootstrap）；1.21.1 那层**没有独立目录**，就是 `src/main` | 1.21.1 与 Fabric 没分开 |
| Loader Adapter | 刚开始：m402 把 networking 收进 `Net`/`ClientNet` 两个漏斗 | 还有 transfer 69 / loader 入口 15 / events 12 / rendering 12 / screenhandler 11 用点没收 |

**唯一实质性分歧**：顾问的 Core 是"见 MC、不见 Loader"，本仓的 Core 是"连 MC 都不见"（`tools_common_gate` 硬闸）。
两者不是对错关系，是取舍：

- **本仓口径**（零 MC）：Core 可以跨 MC 世代原样复用（1.20.1 组件↔NBT 代际差也伤不到它），
  代价是 SPI 只能用 `Object` 不透明句柄（`RecipeAccess` 就是这么写的），牺牲类型安全。
- **顾问口径**（见 MC）：类型安全好写，代价是 MC 类型跨世代会变，每个世代得各留一份 Core。

**推荐第三条路（本仓其实正在自然长出这个形状）：两级 Core**

```
common/        零 MC 纯逻辑           ← 跨全部世代复用（现状，硬闸守住）
xplat/         见 MC、不见 Loader     ← 每个 MC 世代一份；src/main 减去 Fabric 触点就是它
versions/<MC>/<loader>/   加载器实现  ← Fabric / NeoForge / Forge 各一份
```

按这条路，目标形态是：

```
SDZJZ
├── common/                     Core（零 MC，2427 行 → 目标 1 万行以上）
├── xplat/1.21.1/               见 MC 不见 Loader（现 src/main 的 85%）
├── xplat/26.x/                 同上，新世代一份
├── versions/1.21.1/fabric/     现 src/main 的 Fabric 触点（m402 后已收成两个漏斗 + 若干族）
├── versions/1.21.1/neoforge/
├── versions/26.1|26.2/{fabric,neoforge}/
└── versions/1.20.1/{forge,fabric}/   ← 另加 ItemDataAccess（组件↔NBT 代际差）
```

## 四、顺序铁律：先抽口，再搬目录

m180 那次事故（先改写旧家、后建新家，建档半途炸）的架构版：
**先搬目录会得到一个搬不动的死结**——文件挪过去编译不过，只能挪回来，白折腾两轮。
正确顺序是：

1. 按 `tools_loader_scan` 排名逐族抽口（networking ✔ m402 → transfer → loader 入口 → events → rendering → screenhandler）；
2. 某个文件的 MC/加载器触点全部走了口，它自然变成 A 类；
3. 这时候再 `git mv`，**一次成功，编译不断**。

**进度条就是两把尺的数字**：`tools_loader_scan`（离 Fabric 多远）与 `tools_platform_scan`（离 MC 多远）。
m402 已经把 networking 从 124→13 用点、9→3 文件。下一刀 transfer 69 用点。
