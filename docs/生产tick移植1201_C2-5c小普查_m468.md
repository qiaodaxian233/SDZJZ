## 一、版图实测（主线蓝本 SCBE）

两颗路由脑 + 两件配套，合计约 176 行，全在 `block/StructureCoreBlockEntity.java`：

| 件 | 行段 | 行数 | 管什么 |
|---|---|---|---|
| `chainWants` / `chainWants0` | 2807–2884 | 78 | **链需求脑**：递归问「这条链下游有人要 id 吗」 |
| `distribute` / `distribute0` | 3199–3229 | 31 | **分发脑**：两轮垫底把产物按边喂下游 |
| `distributeEven` / `distributeEven0` | 3159–3195 | 37 | 分配器均分（share/extra 整除分账） |
| `accepts` / `accepts0` | 3233–3283 | 51 | 收料判定（单点「你收不收 id」） |
| `nodeBuf` / `BUF_CAP` / `bufTypeOk` / `mergeLegacy` | 73–74、3128、2435 | — | 每节点在途缓存（封顶 200000、类型上限、删节点回收） |

**chainWants 分派表**（按判定序，与 accepts 一一对偶）：暂停→false（m110b）／过滤器→`filterPasses`／
开关→`switchOn`／抽取节点→`extractorLive`+白名单（m160）／垃圾桶→**恒 true**（m153：经逻辑节点
转接=玩家显式布线授权）／虚空处理器→配置开关+白名单（m378）／传感器·分配器→放行（闸在下发阶段
才生效）／自动合成机→`CraftPlanner` 手选条目或全候选并集（`crafterNeeds` 逐节点缓存）／酿造塔→
`BrewPlanner.needs`+燃料（m131b 漏接前科）／附魔工厂→`EnchantPlanner.needs`（m132）／`MachineItem`→
熔炉族走 `SmeltPlanner.resultOf`+白名单，否则 `consumesInputs()` 逐输入比对，免费产出机 false／
其余（农场·笼子）→false。末尾沿 `outT[i]` 递归下探，`depth>8` 硬顶 + `visited` 去环。

**distribute 两轮垫底**（m150 立）：pass0 跳过垃圾桶/虚空处理器，pass1 只喂它们——**垃圾桶永远是
最后去处，与连线先后无关**；每目标过 `accepts` 闸 + `bufTypeOk` 类型上限 + `BUF_CAP` 封顶；
装不下的余量一律 `depositFor` → 定向存储 → `addOutput` 默认路由。**不变量：绝不堵死在下游缓存里。**

**本笔最重要的结构性发现**：`chainWants` 与 `accepts` 是**同一张节点类型表的两面**——一个管
「要不要」（上游主动拉料时问），一个管「收不收」（下游被动收料时问）。**成对写、成对测**：
m131b 只写了 accepts 那面漏了 chainWants，结果「仓→过滤器→酿造塔」的拉料恒不通，直到 m132-6
才实锤（DEVLOG 原话「chainWants 漏接实锤」）。移植时这条是头号回归源。

## 二、地基对表（1.20.1 现状）

**白捡的**：`g.connections`（机器↔机器边，m457 起可摆可连、存档在位、`detachNode` 剪线已对拍）；
`storageEdges`（kind0 产出/kind1 供料，m458/⑤b）；`depositTarget`/`supplyTarget`（⑤a/⑤b）；
四层预算闸（CoreScheduler）；`DropRolls`/`StorageAccess`（白名单已挂）。

**缺口三条**：

1. **在途缓存整套不存在**——`StructureCore120:100` 自留注「nodeBufs 在途缓存随 ⑤c」。
   机器↔机器连线的本质就是「上游产物先落下游节点缓存，下游 tick 时从自己缓存吃」，
   没有缓存就没有路由。连带 `detachNode` 的在途回收支路（蓝本 2435 `mergeLegacy`）也要补，
   否则删节点=丢在途物品。
2. **`NodeTags` 不可挂**（`xplat/node/NodeTags.java`，249 行 59 个 public static 纯函数）——
   6 处 MC 触点：`CustomData`/`ItemStack`/`CompoundTag`/`Tag`/`ListTag`，其中 **`CustomData` 是
   1.20.5+ 专属**（1.20.1 走 `stack.getTag()`）。过滤器/开关/抽取/垃圾桶/传感器/分配器/暂停
   七类判定全部读节点栈 NBT，**逻辑节点语义在本世代拿不到**。
   *好消息*：m451 的 `ItemData.install(new TagItemData())` 已在 `RetroBootstrap:23` 装好，
   m436 五口对位表现成——`NodeTags` 的 NBT 出入口改走 `ItemData` 即可上挂。
3. **规划器族无本世代实现**（`CraftPlanner`/`BrewPlanner`/`EnchantPlanner`/`SmeltPlanner`
   全依赖 RecipeAccess，⑤d 的前置缺口）——两脑的配方域分支本刀只能后置或给黄灯。

## 三、世代取舍（显式记档，照 m463 规矩）

- ⑤c **只做机器↔机器直连**：`accepts` 只留 `MachineItem` + `consumesInputs()` 一支
  （熔炉族除外），零 `NodeTags` 依赖、零规划器依赖——正好覆盖 ⑤b 那 11 台 defConsume 的上游喂料，
  「产线接产线」这个玩法核心本刀就能玩。
- 逻辑节点六件（过滤器/开关/抽取/垃圾桶/传感器/分配器）随 ⑤c2；两轮垫底与分配器均分的**判定**
  都在节点表里，因此跟着一起走，本刀只把 `distribute` 的两轮**壳**先立好（垃圾桶分支恒 false）。
- 配方域分支随 ⑤d。
- 在途缓存数值**逐位照抄蓝本**：`BUF_CAP=200000`、`bufTypeOk` 类型上限口径（m270）——不发明新常量。

## 四、分片（⑤c 三刀）

**⑤c1 在途缓存 + 直连路由**（本刀最肥，落地物）：`nodeBufs` 懒扩容 + `BUF_CAP` + `bufTypeOk` +
删节点回收；`distribute` 两轮壳；`accepts` 单支；产出优先喂下游节点缓存、余量走 kind0 仓。
判官三条：①上游 `cobble_maker` → 下游耗料机 直连产线跑通（下游不接供料仓也能吃上料）；
②下游吃不下时余量必落仓（进出账守恒对账，不许凭空消失）；③类型上限拒收→转默认路由零丢件。

**⑤c2 `NodeTags` 上挂（绞杀者第五刀）**：NBT 出入口改走 `ItemData` 五口 → MC 触点清零 →
进 common 名册 → 白名单挂 1.20.1；随后两脑的逻辑节点七分支**成对**落地 + 垃圾桶两轮垫底 +
分配器均分。改型走 **m366b 类型迁移六项扫描**全套。

**⑤c3 链式拉料**：`chainWants` 递归 + 供料侧接线（蓝本 `topUpSource` 那条 m340）。
判官照 m132-6 同构：仓→过滤器（白名单）→耗料机，拉得动才算过。

## 五、风险三条

1. **成对漏写（最高）**：`chainWants`/`accepts` 同表两面，缺一面就是「静默不产」的哑谜——
   界面上看不出来（m99 家法：静默无效比数值弱更伤）。落刀时把逐分支双列对照表写进 DEVLOG，
   判官**每分支双向各一条**。
2. **`NodeTags` 上挂的连坐面**：它是主线 59 个纯函数的落点，动它=动四线。
   m180 那刀敢说「回归风险按构造为零」是因为**方法体一字未改**；⑤c2 要改出入口，
   **不再是零风险**——必须走「新增 ItemData 走法 + 旧走法原位保留同值」两步，CI 四线共判。
3. **在途缓存的存档面**：`nodeBufs` 入 NBT = 存档结构变更，写读对拍必须同一刀做完
   （m180 教训：先建目录、先写新家、再动旧家）。
