# C2-⑤d 小普查与分片稿（m476，零代码笔）

> 家法：⑤ 这条线每遇到"依赖面明显变大"的分片，先普查后动刀（m463 → ⑤a~⑤c 分片、
> m468 → ⑤c1~⑤c3 分片，两次都因为先量后切而没返工）。⑤d 是规划器族——四台机器
> （自动合成 / 酿造塔 / 附魔工厂 / 熔炉族）全都依赖 `RecipeAccess`，本世代未建，
> 依赖面比前面任何一刀都大，所以照规矩先量。

## 一、结论先行（三条）

1. **好消息：Planner 四件早就在 Common 了**（`CraftPlanner` 320 行 / `EnchantPlanner` 76 /
   `BrewPlanner` 73 / `SmeltPlanner` 67，零 MC 依赖）。本世代**一行业务逻辑都不用重写**，
   只需补一个平台实现 `RetroRecipeAccess`（八口）把配方查询接上——这是 m362~m373 那几刀
   （配方域 SPI + 拆四域接口 + 26.x 分域适配器）攒下的红利，第一次由 1.20.1 来兑现。
2. **坏消息：目标选择 UI 在本世代完全不存在**。自动合成/酿造/附魔三台的"做什么"存在节点栈
   `ct`（craftTarget）键上，由屏侧二级界面写入——本世代 retro 屏 `ct` 键**零触点**。
   后端落了也没人能给它设目标，等于摆件。**这是 ⑤d 的硬前置，且它是 UI 活不是路由活。**
3. **熔炉族是唯一可独立交付的一台**：万能熔炉"接什么烧什么"，目标由 m149 的白名单
   （`fl` 键，NodeTags 已上挂）表达，**不需要目标 UI**。所以 ⑤d 应当先切出熔炉族单独一刀，
   它一落地就是本模组招牌机之一在 1.20.1 可玩。

## 二、依赖面量清

### 2.1 `RecipeAccess` 八口（Common 侧接口，m368 已拆四域）

| 域 | 方法 | 1.21 实现要点 | 1.20.1 对位成本 |
|---|---|---|---|
| Craft | `craftingPlans(level, targetId)` | `getAllRecipesFor(CRAFTING)` → `RecipeHolder` 包装、`entry.id()`、`getResultItem(registryAccess)`、`Ingredient.getItems()` | **低**。差三处：1.20.1 无 `RecipeHolder`（直接是 `CraftingRecipe`）、id 走 `r.getId()`、`ResourceLocation.parse` → `new ResourceLocation`（retro 侧到处是先例） |
| Craft | `craftRemainderOf(itemId)` | `Item.getCraftingRemainingItem()` | **极低**。只差 ResourceLocation 构造 |
| Smelt | `smeltingCandidates(level)` | 同 Craft，`RecipeType.SMELTING` | **低**。同上三处 |
| Brew | `brewingPlan` / `brewTargetStack` | `PotionContents` 组件、`world.potionBrewing()` 实例、`PotionContents.createItemStack`、`BuiltInRegistries.POTION.getHolder` | **中**。1.20.1 药水存 NBT（`PotionUtils.getPotion/setPotion`）、酿造注册表是**静态类** `BrewingRecipeRegistry.isIngredient/.mix`、`isSameItemSameComponents` → `isSameItemSameTags`。**BFS 前驱树结构一字不动**，只换取/设药水与混合三处 API，约 60 行 |
| Ench | `enchantingPlan` / `enchantTargetStack` / `enchantTargetName` | 附魔已数据包化：`Holder<Enchantment>`、`registryAccess().lookupOrThrow(Registries.ENCHANTMENT)`、`book.enchant(holder, lv)`、`Enchantment.getFullname(holder, lv)`、`ench.getAnvilCost()` | **中，且有一处语义缺口**（见 2.2）。1.20.1 附魔是内置注册表 `BuiltInRegistries.ENCHANTMENT.get(rl)` → `Enchantment` 对象、附魔书走 `EnchantedBookItem.addEnchantment(stack, new EnchantmentInstance(ench, lv))`、名字 `ench.getFullname(lv)` |

### 2.2 唯一的真实语义缺口：附魔定价的 `getAnvilCost()`

蓝本 `enchResolve` 里经验价 = `max(1, entry.value().getAnvilCost() / 2) × 等级 × XP_PER_WEIGHT`。
`getAnvilCost()` 是**附魔数据包化之后**才有的字段，1.20.1 的 `Enchantment` 没有直接对位
（同期表达"这附魔多贵"的是 `Rarity.getWeight()`，m101 交易所定价用过）。

这不是抄漏，是**上游语义本身在两代之间变了**。两条路，都要作者拍板，不擅自选：
- **A. 按 rarity 反推**：用 `getRarity().getWeight()` 折一张对照表贴近 1.21 的 anvilCost 分布——
  两代**数值接近但不保证逐位相等**，跨代同一附魔的经验价可能差一两点。
- **B. 常量表硬编码**：把 1.21 的 anvilCost 抄成一张 `id → cost` 表放 Common，两代同表——
  **逐位相等**，代价是原版加新附魔时要手动补表（正是 m470 那类"手抄名单"漏点，得配对表闸）。

普查倾向 B 配闸（本项目已有第 16/17 两把对表尺子，加一条项即可），但**等作者定**。

### 2.3 四台机器的 tick 分支（蓝本 `tickInner` 段）

| 机器 | 蓝本行数 | 依赖 | 本世代阻塞项 |
|---|---|---|---|
| 熔炉族 | ~59 | `SmeltPlanner` + m149 白名单 | **无**（白名单键 `fl` 已上挂）。可独立交付 |
| 自动合成 | ~59 | `CraftPlanner` + `ct` 目标 | 目标 UI |

### 2.4 经验池的咬合关系（⑤d 与 ⑤e 不是并列，是交叉）

- **存储核心侧的 `xpBank` 已在**（`StorageCore120:138` 起，`xpAdd`/取用齐全，m4xx 存储线带过来的）。
- **结构核心侧的 `xpPool` 不存在**。蓝本里附魔工厂吃的是 SCBE 的 `xpPool`，而这个池子的进项是
  熔炼产出与虚空处理器（⑤e）。也就是说：**附魔工厂（⑤d 的一台）依赖 ⑤e 的池子**。
- 结论：⑤e 的"池子本身"（字段+存档+进出口）应当**先于附魔工厂**落地，或与之同刀。
  这是本次普查最值钱的一条——按原计划的 ⑤d→⑤e 顺序直接做，做到附魔工厂会卡住。

### 2.5 白捡的红利：契约判官现成

`common/.../RecipeDomainAssertions.java`（169 行，m372 作者拍板 A 线）是**跨版本行为不变量**：
26.2 的 `ModernRecipeDomainTests` 就是喂自己的 `ModernRecipeAccess` 跑**同一套**七类断言
（任意木板 / 候选组同口径 / 熔炼稳定选序 / Ingredient 枚举口径 / 合成残留双口 / 酿造全路径 /
附魔成本语义）。1.20.1 只要装上 `RetroRecipeAccess`、把 `RecipeDomainAssertions` 加进
白名单、写一个五行的 `RetroRecipeDomainTests`，**七类断言立刻全跑**——不用自己想验什么。
注意第七类"附魔成本语义"正好压着 2.2 那个缺口，作者选 A 还是 B 会直接反映在这条断言上。

## 三、分片稿（四刀，顺序有依赖）

- **⑤d1 `RetroRecipeAccess` 四域 + 契约判官**：craft/smelt 两口（低成本）先行，brew/ench 走
  26.2 同款**分域适配器**结构（`RetroBrewAccess`/`RetroEnchantAccess`，聚合类只转发，m368 意图）；
  装配位 = `RetroBootstrap` 的 `installIdent` 下一行（`Platform.initRecipes`）；
  验收线 = `RecipeDomainAssertions.runAll` 七类断言全绿。**2.2 的缺口在这刀撞上，需作者先拍板。**
- **⑤d2 熔炉族 tick**：唯一无 UI 依赖的一台，`accepts`/`chainWants` 两面的 `smelterFamily` 行
  同刀成对划掉（m473 已各留标了刀号的到序行）；判官照 ⑤b 的确定性对数形（铁矿→铁锭）。
  **这刀一落，万能熔炉在 1.20.1 可玩。**
- **⑤d3 目标选择 UI + 自动合成机**：屏侧二级界面（`ct` 键写入）+ `CraftPlanner` 接线。
  这刀一半是 UI 活，建议单独开，别和路由混在一起（m465 插队刀的教训：UI 和逻辑同刀时
  实机反馈回来分不清是哪半坏了）。
- **⑤d4 酿造塔 + 附魔工厂**：附魔工厂**必须等 `xpPool`**（见 2.4）——要么把 ⑤e 的池子提前到
  这刀之前，要么本刀先做酿造塔、附魔工厂并入 ⑤e。
