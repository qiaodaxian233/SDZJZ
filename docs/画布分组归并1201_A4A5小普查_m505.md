# 画布分组（A5=m192）+ 连线归并徽章（A4=m193）小普查（零代码笔）

> B 线业务代码 m504 收官后按取活规则第 3 条转 A 线收尾项。作业表里 A4/A5 互相把对方列成
> 依赖（A4→A5、A5→A4），动手前先厘清方向；顺带发现服务端那半其实早就具备真移植条件，
> 值得先普查再分片——规模与依赖面都不小，且是本会话第一次碰 client 渲染/交互/网络协议
> 这三块，风险与 B 线纯后端账本逻辑不是一个量级。

## 一、依赖方向：A5 先于 A4（表述已订正）

主线 `StructureCoreScreen.java` 第 590 行原注写得很直白：

> "m193 分组共享表一次算好：组成员 / 组框矩形 / 节点→组查表（组框渲染与连线归并共用）"

归并（m193）的锚点算法是"端点属组→锚到组框缘"——没有组就没有"组框缘"这个锚点，归并
无从谈起。**作业表原表述"A5 依赖 A4"是笔误**（大概率是历史某次编辑把两行依赖列反了），
已在作业表里订正为 A5 无依赖、A4 依赖 A5。

## 二、服务端：数据结构与业务方法早已具备真移植条件

逐句核对下来，"分组"这块业务在服务端几乎是**又一次 B 线故事的重演**：

- **数据结构已共用**：`CanvasGraphState.groupNames`（`Map<Integer,String>`，组号→组名）
  与它的存档读写，从 m477（真移植 A 阶段第一刀，图状态两代合一）起就是两代同一份代码。
  成员归属走 `NodeTags.nodeGroup(ItemStack)`（读节点栈 NBT 的 `gp` 字段），`NodeTags`
  整个文件从 m472 起也已两代共用。**本世代 `StructureCore120` 已经有同一个 `g` 字段
  （`CanvasGraphState` 实例）**，跟主线结构逐位一致。
- **业务方法未共用，但零 MC 1.21 专属 API**：主线 `StructureCoreBlockEntity` 里
  `createGroup`/`dissolveGroup`/`renameGroup`/`moveGroup`/`setNodeGroupTag`/`sweepGroups`
  六个方法（约 75 行，2467~2540 附近）逐句读下来，**只用到已共用的类型**
  （`g.machineNodes`/`g.groupNames`/`NodeTags.nodeGroup`/`ItemData.copyOf`/`ItemData.write`/
  `ItemStack`/`CompoundTag`）加上一个纯算术的 `clampCanvas(long)`（钳幅，零 API）。
  跟 BE 生命周期打交道的只有 `setChanged()` 与 `syncToClient()` 两个调用点——这正是
  `StorageLedger` 那套 `Runnable onChange` 解耦手法的用武之地。**这六个方法真移植下沉的
  可行性，和 B 线任何一次账本方法下沉相比没有本质区别。**
- **同步机制是执行面差，不是数据差**：主线走"服务端脏检测（`canvasDirty`）+ 版本号
  （`snapshotRev`）+ 观众登记表（`canvasViewers`）+ 按需推送"（`flushCanvasSnapshot`，
  每 tick 检查）；本世代走"客户端主动 `CanvasQuery` → 服务端当场编码 `CanvasSnapshot`
  回发"（挂在 `StructureCoreMenu120::handleQuery`，无观众态）。两者都是把
  `CanvasGraphState`（含 `groupNames`）编码进快照发给客户端，**分组数据只要写进
  `groupNames`，两代现有的快照通道原样能带到客户端**——不需要为"读组数据"这件事
  另开一条网络协议。这与 m480 记档"只有主线有观众态，不为接口好看造对位"同一律：
  执行面（推/拉、有无观众表）不同不代表数据不能共用，此处不需要也不该强行统一执行面。

**结论：服务端这半真正缺的，只是"客户端发起写请求"这条通路**——本世代需要新的网络包
（对位主线 `NodeGroupPayload`/`NodeGroupMovePayload`，走 `FabricPacket` 而非
`CustomPacketPayload`，样板照抄已有的 `NodePayloads120.java`）与一个接收器（分派到
下沉后的组操作方法），不需要另建数据结构，也不需要额外的"读"协议。

## 三、客户端：真正的大头，且不可共用

这半没有捷径——1.20.1 与 1.21 的 `Screen`/`GuiGraphics`/事件签名差异很大，主线
`StructureCoreScreen.java`（3177 行）里的 m192/m193 相关代码**高度耦合这个类自己的
渲染管线调用与一整批状态字段**（`selected`/`dragGid`/`dragGidDx/Dy`/`boxSelecting`/
`boxX0/Y0/X1/Y1`/`renameGid`/`renameField` 等），不是"抽出一个纯函数"就能解决的形状，
必须在 `CanvasScreen120.java` 里照 1.20.1 的 API 重新落笔（**参照主线原文逐句对，不是
凭空重新设计**——m484 那次"有原版不看、自己编坐标"的教训写在纪律里，这次不重蹈）。

粗量规模：`m192`/`m193` 标记在主线文件里各出现 22 / 8 处，分布在：

| 区块 | 大致范围 | 内容 |
|---|---|---|
| 渲染：组框 + 归并线 + 选中框 | 590~800 附近（含穿插的非分组代码） | 组框矩形/标题带/归并共享表/彗星徽章 |
| 辅助方法 | 1337~1480 附近 | `groupsOn`/`groupMembers`/`groupRect`/`groupOfNode`/`createGroupFromSelection`/`openGroupMenu`/`openRename`/`closeRename`/`confirmRename`/`renderRename` |
| 归并线主体 | 1736 起一段 | m193 端点→组框缘锚点与徽章绘制 |
| 鼠标事件穿插判断 | 1935/2305/2316/2426/2433/2444/2449/2477/2488/2613/2620/2625 | 组合快捷键、右键组菜单、Shift 框选、拖动组框、松手发包 |
| 键盘事件穿插判断 | 3130/3146/3148/3158/3162/3172 | 重命名窗回车/Esc、F2 重命名、G 键打组 |

**这些区块大多"夹在"更大的通用方法里**（`mouseClicked`本身管全部交互不只是分组），
照行号盲切会重演 m487 血案——`connectedComponent`/`hoveredNode`/`openPrimaryPicker`
就恰好夹在 1337~1480 那段辅助方法区间里但根本不是分组专属，验证过一次才敢确认边界。
两代客户端代码量粗估在 300~450 行区间（本世代新写，非共用）。

## 四、分片方案（四刀，每刀可独立提交回滚）

1. **A5a（服务端）**：六个组操作方法下沉共用件（`CanvasGraphState` 自己的方法，
   `setChanged`/`syncToClient` 走 `Runnable onChange` 解耦，同 `StorageLedger` 手法）；
   两代 BE 各留转发；新建 1.20.1 网络包对位（参照 `NodePayloads120.java`）+ 接收器注册
   （分派到下沉后的方法）。此刀完成后服务端具备完整分组能力，但 1.20.1 客户端还看不见——
   可先用主线客户端 + 判官测试验证服务端逻辑，1.20.1 那半留到下一刀再联调。
2. **A5b（客户端读+渲染）**：`CanvasScreen120` 新增组框渲染（读 `groupsView()` 与每节点
   `gp` 标记算组框矩形+标题带），先只读不写——无框选、无拖动、无菜单，验证组框画得对、
   随存档持久化正确。
3. **A5c（客户端写+交互）**：框选状态机、G 键打组、拖动组框整体移动、右键菜单
   （重命名/解散）、重命名小窗——补全 A5 全部交互面，接上 A5a 建好的网络包。
4. **A4（归并徽章）**：m193 归并线计算与渲染，依赖 A5c 全部完成（分组交互齐了才好联调
   "端点属组→锚到组框缘"这条锚点算法）。
